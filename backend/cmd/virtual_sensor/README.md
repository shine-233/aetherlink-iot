# 虚拟传感器目录说明

`backend/cmd/virtual_sensor` 是本地虚拟设备入口目录，用于模拟温湿度传感器与后端 MQTT 链路联调。

## 目录职责

- 启动一个常驻进程，持续向 MQTT broker 发布模拟设备消息。
- 提供控制消息订阅、遥测消息发布、属性消息发布和事件消息发布能力。
- 作为本地联调工具，帮助验证后端设备协议、topic 约定和消息解析逻辑。

## 文件关系

- `main.go` 是进程启动入口，负责拉起虚拟温湿度模拟器。
- `mqtt_client.go` 封装 MQTT 客户端创建、连接和断线重连。
- `temp_hum_sensor.go` 负责消息构造、订阅控制和各类 payload 发布。
- `sensor.sh` 是辅助脚本，和 Go 入口配合使用。

## 重点文件

- `main.go`：进程入口和消息 ID 生成逻辑。
- `mqtt_client.go`：MQTT 连接参数、自动重连和回调注册。
- `temp_hum_sensor.go`：模拟数据生成、topic 拼接和发布节奏控制。

## 当前静态审查结论

- 目录内存在较多硬编码 broker、账号和设备标识，适合本地调试，但不适合公开配置。
- 消息 topic、payload 字段和发布频率是后端联调契约，修改时必须同步后端消费逻辑。
- 部分函数依赖全局 MQTT 客户端状态，调用顺序必须稳定，否则容易出现空指针或订阅失败。

## 改进方案

- 把 broker、用户名、密码和设备 ID 改为环境变量或本地配置文件读取。
- 把 topic、发布周期和子设备标识整理成配置常量，减少散落在代码里的协议约定。
- 对关键发布链路补充更明确的 README 说明，避免联调时误改消息结构。

## 建议实施步骤

1. 先确认本地 MQTT broker 地址和账号是否可用。
2. 再确认 topic 命名和消息字段是否与后端设备协议一致。
3. 最后把硬编码配置逐步迁移到外部配置，再保留默认值做本地调试兜底。

## 预期效果

- 本地联调入口更清晰，开发者更容易理解消息流。
- 降低泄露 broker 和设备信息的风险。
- 让虚拟设备和后端协议的静态审查更可追踪。

## 静态审查重点

- MQTT broker、账号和设备 ID 是否仍然硬编码。
- 遥测、属性和事件的 topic 是否和后端约定一致。
- 发布节奏和重连逻辑是否会对本地调试造成阻塞或误判。
