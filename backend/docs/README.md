# 后端文档与 Swagger 目录

## 目录定位

`backend/docs` 保存后端 API 文档、Swagger/OpenAPI 生成物、API 标准化说明、开发辅助规范和设计文档。它是后端开发、接口联调、代码审查和发布前文档核对的重要入口。

## 主要文件与子目录

- `docs.go`：由 `swaggo/swag` 生成的 Swagger Go 注册代码，不要手工改业务内容。
- `swagger.json`、`swagger.yaml`：Swagger/OpenAPI 输出，用于接口查看、联调和发布前 API 审查。
- `README-DEV.md`：后端开发辅助说明。
- `API标准化/`：API 分层、路由、处理器、服务层和生成文件维护说明。
- `code_help/`：代码结构、Go 编码规范、AI 辅助开发和开发标准文档。
- `设计/`：自动化场景、用户扩展字段、在线离线等业务设计材料。

## 文件关系

路由和处理器注释变化后，应重新生成 `docs.go`、`swagger.json` 和 `swagger.yaml`，再结合 `API标准化/` 与 `code_help/` 检查接口分层是否一致。`docs.go` 和 `swagger.*` 是由 API 注释生成的快照，源码中的路由注册、处理器注释和运行验证才是当前行为的来源；未重新生成或未运行验证时，不应把这些文件当作完整的当前路由清单或运行结果。设计文档用于解释业务意图，不应替代当前源码和测试结果。

## 审查记录与重构建议

- 问题描述：Swagger 生成物、开发规范和历史设计文档混放，若缺少目录说明，维护者容易误把生成物当作手写代码修改。
- 改进方案：明确 generated 文件边界，为每个说明目录补 README，并把生成命令、接口分层和发布验证放到固定文档入口。
- 实施步骤：先补目录 README，再在后续发布批次中补充 Swagger 生成命令和 CI diff 检查。
- 预期效果：降低 API 文档漂移风险，让 GitHub 读者能快速区分“当前接口契约”和“历史设计材料”。

## 验证建议

- 修改接口注释或路由后重新生成 Swagger，并检查 `swagger.json`/`swagger.yaml` 是否只包含预期差异。
- 修改 API 行为后同步运行相关后端 Go 测试和自动化 API 契约测试。
