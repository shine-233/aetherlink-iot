# initialize 目录说明

`backend/initialize` 负责后端启动阶段的基础设施初始化。这里的代码不直接承载业务编排，但会决定配置加载、日志输出、数据库连接、Redis 连接、权限引擎、限流器、自动化缓存和定时任务等全局依赖是否按预期进入运行态。

## 职责

- 提供配置入口，统一读取 `viper` 配置并为其余初始化逻辑提供参数。
- 建立 PostgreSQL、Redis、Casbin、日志、RSA 私钥等全局基础设施。
- 提供自动化缓存、告警缓存、限流器和定时任务初始化所需的启动支撑。
- 为其它包暴露“启动期一次性初始化”的公共入口，避免业务层重复拼装底层依赖。

## 关系

- `viper_init.go` 为数据库、Redis、日志等初始化提供配置来源。
- `log_init.go` 先决定日志输出方式，`pg_init.go` 再复用 SQL 日志 writer。
- `pg_init.go` 负责数据库初始化，并在成功后触发 `casbin_init.go` 的权限引擎装配。
- `redis_init.go` 为 `alarm_cache.go`、`automate_cache.go`、`croninit/device_stats.go` 等 Redis 依赖模块提供客户端。
- `automatecache/` 只定义自动化缓存的设备维度适配器，供 `automate_cache.go` 组合使用。
- `automate_cache.go` 通过目录内窄 Redis interface 访问 `GET/SET/DEL/SCAN`，生产仍使用全局 Redis client，测试可替换为内存 adapter 验证缓存回收行为。
- `croninit/` 负责真实定时任务注册与启动实现。

## 2026-07-18 自动化缓存验证补充

- `DeleteCacheBySceneAutomationId` 的公开行为已有内存 adapter 测试，覆盖动作缓存缺失、条件组缓存缺失、单设备/同类设备两种维度和保留同设备其它场景。
- 该 seam 只收窄 Redis 命令依赖，没有改变生产缓存键、过期时间或全局 Redis 装配方式；真实 Redis 仍需作为目标环境 adapter/runtime 证据。

## 审查结论

- 该目录当前主要风险不在算法复杂度，而在“全局状态 + 启动副作用”叠加后带来的维护成本。
- 多个文件已经具备基础注释，但目录级职责、依赖顺序和缓存/定时任务之间的关系说明仍然不足。
- 本次仅补充静态文档和注释，不调整任何启动顺序、重试策略、缓存键规则或定时表达式，行为应保持不变。

## 方案

- 为每个目标源码文件补充统一风格的中文文件头，明确职责、依赖和维护边界。
- 为关键函数补充“做什么、依赖什么、输出什么”的注释，降低审查与交接时的理解成本。
- 为 `initialize`、`automatecache`、`croninit` 三个目录补齐职责、关系、审查结论、执行步骤和预期效果说明。

## 步骤

1. 逐文件确认真实代码职责、全局变量、关键入口和对外暴露函数。
2. 只在允许路径内补充文件头注释、关键函数注释和目录 README。
3. 复核注释是否与现有实现一致，避免出现注释承诺超出代码真实行为的情况。
4. 保持所有业务语句、调用顺序、常量值和返回逻辑不变。

## 预期效果

- 审查者可以更快确认启动链路中的职责边界和依赖关系。
- 后续维护者在修改缓存、定时任务或基础设施初始化时，更容易识别受影响范围。
- 在不改业务逻辑的前提下，提升该目录的可读性、可审查性和交接效率。
