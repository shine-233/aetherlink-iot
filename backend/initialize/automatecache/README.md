# automatecache 目录说明

本目录保存自动化缓存的“设备维度适配器”。它们本身不连接 Redis，也不装配场景或动作数据，只负责告诉上层缓存模块：当前应使用什么缓存前缀、什么触发条件类型来区分单一设备与单类设备两种路径。

## 职责

- 为自动化缓存提供统一的设备维度抽象。
- 隔离缓存前缀和条件类型常量，避免上层到处硬编码。
- 支撑 `automate_cache.go` 在不同触发模型下复用同一套缓存流程。

## 关系

- `device_one.go` 提供单一设备触发维度适配器。
- `device_multiple.go` 提供单类设备/多设备触发维度适配器。
- 两者都由 `backend/initialize/automate_cache.go` 在读写缓存前动态切换使用。

## 审查结论

- 目录结构很轻，职责单一，主要风险集中在“返回值被上层缓存键规则强依赖”。
- 当前代码可读性尚可，但目录级说明不足，容易让维护者误以为这里直接负责 Redis 操作。
- 本次仅补足职责和关系说明，不改变任何前缀、常量或接口形态。

## 方案

- 说明该目录只提供维度适配，不处理真实缓存。
- 标明每个适配器与上层 `automate_cache.go` 的协作关系。
- 强调前缀与条件类型的稳定性要求，帮助审查者快速识别风险点。

## 步骤

1. 确认两个适配器分别返回的缓存前缀和条件类型。
2. 核对这些返回值在 `automate_cache.go` 中的使用方式。
3. 以目录 README 固化职责边界和维护注意事项。

## 预期效果

- 维护者能更快理解该目录为何存在，以及它不负责什么。
- 在新增触发维度或调整缓存规则时，更容易先定位到需要同步检查的上层代码。
- 审查时可更明确地区分“适配器变更”和“缓存逻辑变更”两类影响面。
