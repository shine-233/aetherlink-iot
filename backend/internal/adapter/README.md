# 后端适配器层

`backend/internal/adapter` 保存后端领域逻辑与外部接口、底层协议或运行时桥接层之间的适配代码。

适配器的职责是“翻译”和“桥接”，而不是决定业务规则本身。若在这里混入租户边界、权限判断或产品策略，后续会很难判断问题究竟属于外部契约还是业务逻辑。

## 目录职责

- 连接后端内部模型与外部接口、协议或下层实现。
- 负责输入输出结构转换、错误透传和桥接层兼容处理。
- 为 `service/` 提供更稳定的外部交互封装。
- `casbinadapter/` 通过应用已有的 GORM 连接读写 `casbin_rule`，保留 Casbin 持久化契约；它不自行连接或迁移数据库，也不增加部署服务。生产默认仍使用 PostgreSQL，纯 Go SQLite 仅用于隔离测试。

## 维护边界

- 业务判断、权限校验和租户边界应继续留在 `internal/service`。
- 适配器应尽量显式说明依赖的外部契约、字段假设和错误行为。
- 若修改适配器输入输出或错误语义，后续需要同步核对调用方和兼容说明。

## 审查与重构建议

### 发现的问题

- 适配器层最容易隐藏“外部系统其实就这么约定”的隐式前提。
- README 过薄时，新维护者很难分清这里是桥接层还是业务层。
- `mqttadapter` 已经同时承载 broker 连接、topic 协议、上行解析、ACK 发布和共享订阅策略，职责密度偏高。
- `message.go` 里的消息类型字符串会外溢到调用方，若继续扩张而没有集中约束，后续很容易出现同义不同名。

### 改进方案

- 为每个适配器文件补足输入、输出、失败行为和兼容边界说明。
- 保持“桥接在 adapter，业务在 service”的分层纪律。
- 对 MQTT 适配器这类高风险桥接层，逐步把连接管理、topic 模板、payload 验证和消息分发拆成更清晰的子职责。
- 对消息类型和 metadata 字段逐步建立更明确的契约，减少散落的字符串判断。

### 预期效果

- 外部契约变更时更容易快速定位影响面。
- 减少桥接层和业务层职责漂移。
