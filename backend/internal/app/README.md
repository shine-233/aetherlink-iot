# 后端应用装配层

`backend/internal/app` 负责 AetherLink IoT 后端的应用级装配逻辑，用来把配置、路由、服务容器和运行入口拼接成可启动的后端进程。

这里通常不是业务规则本体，但它一旦出问题，会直接影响服务启动、路由暴露、依赖注入和部署可观测性，因此依然属于高敏感目录。

## 目录职责

- 组织应用级启动流程与服务初始化顺序。
- 串联配置、路由注册、HTTP 服务生命周期和运行时基础设施。
- 为其他内部模块提供装配层入口，而不是承载具体业务规则。

## 维护边界

- 业务判断、租户权限和领域规则应继续留在 `service/`，不要在装配层下沉业务逻辑。
- 路由暴露、HTTP 服务配置和启动日志调整可能会影响部署排障与自动化预期，应谨慎修改。
- 涉及监听地址、启动顺序、优雅关闭或 panic 兜底时，后续需要单独进入运行期验证清单。
- 后台 worker 的 shutdown interface 必须可取消；不能只让 `Stop()` 超时返回，却把底层数据库调用留在后台继续执行。

## 本轮已确认整理

- `http_service.go`
  - 中文化启动、监听、停止和启动横幅文案。
  - 保留原有服务生命周期逻辑不变。
- `telemetry_dead_letter_worker.go`
  - worker 的 drainer seam 现在接收 `context.Context`；启动即 drain、周期 drain 和停机 final drain 复用同一小 interface。
  - `Stop()` 在同一 `shutdown_timeout` 预算内取消正在运行的 drain、等待循环退出，再执行一次带 deadline 的 final drain，不再通过放弃等待来遗留不可控 goroutine。
  - 默认 adapter 把 context 传入 telemetry dead-letter service；测试 adapter 可直接观察取消，锁定停机行为而不连接真实数据库。

## 审查与重构建议

### 发现的问题

- 应用装配层虽然代码量不一定大，但任何修改都容易全局影响启动行为。
- 如果 README 过薄，维护者容易把这里误当成普通工具目录，忽略其部署敏感性。

### 改进方案

- 保持装配层 README 和文件头对“谁负责启动、谁负责路由、谁负责关闭”写清楚。
- 后续若继续收敛启动逻辑，优先抽取不改变行为的小 helper，而不是直接大改入口。

### 建议实施步骤

1. 先明确配置加载、HTTP 服务构建和生命周期控制的职责边界。
2. 再把重复日志、横幅或启动兜底逻辑收敛成局部 helper。
3. 静态批次完成后，再统一做启动/关闭/监听路径验证。

### 预期效果

- 部署问题更容易定位，维护者能更快判断故障落点。
- 入口代码更易读，后续做环境适配或服务拆分时更稳。
