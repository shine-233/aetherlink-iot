# 后端上行链路说明

`backend/internal/uplink` 是设备上行消息进入业务系统后的核心处理目录，负责把来自 MQTT 或内部总线的设备数据，按消息类型分发到遥测、属性、事件、状态和响应等不同处理链路中。这个目录是“协议世界”与“业务世界”的第一道关键边界，上游连着设备与 broker，下游连着存储、自动化、设备在线状态、通知和诊断能力。

如果说 `dal` 关注“数据怎么落库”，那么 `uplink` 关注的是“设备发上来的东西如何被正确识别、分流、加工并触发副作用”。因此，这个目录的改动往往不是局部影响，而是会同时波及：

- 前端设备详情与实时状态展示
- 遥测与事件历史
- 自动化触发条件
- 在线离线判断
- 下发响应闭环
- MQTT 兼容行为与网关子设备场景

## 目录职责

- 接收并组织不同类型的设备上行消息处理流程。
- 为遥测、属性、事件、状态、响应等消息建立统一的分发骨架。
- 协调 `processor`、`storage`、`dal`、`service` 等后端模块完成业务副作用。
- 管理上行处理器的生命周期、上下文取消和部分并发协作边界。
- 为设备在线通知、自动化触发、诊断和兼容性逻辑提供统一接入点。

## 典型依赖关系

这个目录大致位于以下调用链中：

`broker / mqtt ingress / internal bus -> uplink.Bus -> UplinkManager -> specific uplink worker -> dal/service/storage/automation side effects`

其中：

- `Bus` 提供消息分发和通道管理能力。
- `UplinkManager` 负责把总线与各类处理器组织起来并统一启动/关闭。
- 各类 `*Uplink` 负责特定消息类型的解码、校验和后续副作用调度。
- 下游会进入：
  - `storage` 写入原始消息或结构化数据
  - `dal` 做状态、事件、历史等数据库持久化
  - `service` 执行业务编排，如心跳、自动化、通知等
  - 诊断、日志或其他平台级副作用

## 目录内文件关系

### 总线与流程编排

- `bus.go`
  - 上行消息的内部总线抽象，负责消息投递、通道组织和关闭边界控制。
- `uplink_manager.go`
  - 目录级流程管理器，统一持有并启动各类消息处理器，是阅读本目录的首选入口。
- `errors.go`
  - 定义总线关闭等基础错误语义，帮助上层区分正常停机与异常失败。

### 各消息类型处理器

- `telemetry.go`
  - 遥测上行处理器，负责解析遥测 payload、接入存储链路、刷新心跳并触发后续业务动作。
- `attribute.go`
  - 属性上行处理器，职责通常与设备属性同步和属性历史留痕相关。
- `event.go`
  - 事件上行处理器，涉及事件入库、自动化事件触发、RDI 或 OTA 进度类业务副作用。
- `status.go`
  - 状态上行处理器，负责设备在线状态、状态诊断以及前端可见的上下线语义更新。
- `response.go`
  - 响应类消息处理器，承接设备对指令、控制、配置等动作的回执闭环。

### 辅助逻辑

- `device_online.go`
  - 设备在线广播、期望数据联动、在线自动化触发等辅助副作用逻辑。

### 测试文件

- `bus_test.go`
- `status_response_test.go`

这两个测试文件说明当前目录至少有基础总线与状态/响应行为验证思路，但从目录复杂度看，仍不足以完全覆盖消息形态差异、并发关闭和多副作用顺序风险。

## 关键调用链

### 1. 上行总控链路

建议先从这条链路建立整体认识：

`Bus -> UplinkManager.Start -> specific Uplink worker Start -> payload decode -> downstream side effects`

这条链路决定了：

- 哪些消息类型会被监听
- 不同处理器由谁创建和持有
- 关闭时如何传播取消信号
- 是否存在某类处理器缺失但总流程仍继续运行的情况

### 2. 遥测链路

典型路径通常是：

`device telemetry message -> TelemetryUplink -> processor/storage -> heartbeat refresh -> telemetry persistence / automation related side effects`

要点：

- 遥测不只是“写历史数据”，还可能隐含在线判断和自动化触发前提。
- 如果 payload 结构变化，前端图表、告警规则和自动化条件都可能受到影响。
- 存储写入与后续副作用的顺序需要保持清晰，否则容易出现“数据已展示但状态未更新”或反过来的时序问题。

### 3. 事件链路

典型路径通常是：

`device event message -> EventUplink -> event persistence -> heartbeat or gateway handling -> automation / OTA / business side effects`

要点：

- 事件链路常比遥测更“业务化”，因为一个事件可能直接驱动自动化或任务状态流转。
- 网关设备与子设备事件递归处理是高风险点，必须保持设备身份解析一致。
- 失败隔离要明确，避免某个业务副作用失败拖垮整个事件处理主链。

### 4. 状态链路

典型路径通常是：

`status message -> StatusUplink -> online/offline persistence -> device status broadcast -> frontend visible state`

要点：

- 设备在线状态与前端设备列表、详情页、自动化在线触发逻辑直接相关。
- 如果状态与遥测/事件都能刷新在线时间，必须清楚谁是权威来源、谁是补充信号。
- 状态变更频繁时，要关注去抖、重复通知和状态抖动问题。

### 5. 响应链路

典型路径通常是：

`device response message -> ResponseUplink -> correlate command/request -> update command result or logs`

要点：

- 响应类消息往往影响“下发是否成功”的用户感知。
- 如果回执解析不稳，会导致前端看到命令卡住、状态不刷新或日志不闭环。
- 需要特别明确 request id、设备 id、命令类型之间的关联策略。

## 静态审查重点

### 1. 单个处理器承担的副作用过多

从 `telemetry.go`、`event.go`、`status.go` 可以看出，部分处理器不只是“解码并转发”，还可能同时承担：

- payload 解析
- 设备身份识别
- 心跳刷新
- 存储写入
- 自动化触发
- 在线广播
- 诊断记录

这会造成两个问题：

- 阅读时很难一眼看出主链和副作用边界。
- 修改任意一步都可能影响其他路径。

建议：

- 先标清“主链动作”和“附加副作用”。
- 再把自动化、在线通知、诊断等副作用逐步下沉为更小 helper。

### 2. 并发关闭与通道退出边界

这个目录天然带有 goroutine、channel、context cancel 等并发元素。高风险点包括：

- `Bus` 关闭后是否仍可能继续投递消息。
- 处理器停止时是否存在 goroutine 泄漏。
- 某类处理器阻塞时是否会反向拖住其他类型消息。

建议：

- 在 README 和代码注释里统一说明关闭顺序。
- 区分“正常停机错误”和“异常处理错误”。
- 后续若补测试，优先覆盖关闭、取消和总线关闭后的行为。

### 3. 消息形态兼容风险

上行链路最怕“看起来只改了一个字段名，实际上影响整个接入链”。风险主要包括：

- 遥测、属性、事件、状态 payload 形态不统一。
- 网关设备和直连设备的设备标识解析规则不一致。
- 某些字段既参与存储又参与自动化判断，改动后双侧语义分裂。

建议：

- 在关键处理器里明确 payload 契约和最小必要字段。
- 对网关/子设备路径单独标注，不要把它们混成普通直连设备逻辑。

### 4. 状态更新与前端感知存在耦合

`status.go` 与 `device_online.go` 这类文件本质上会影响前端是否认为设备在线，以及自动化是否认为设备刚刚恢复连接。

风险在于：

- 状态刷新来源过多，语义不统一。
- 在线广播和数据库状态写入顺序不清晰。
- 期望值、在线通知、自动化触发三者可能重复或错位。

建议：

- 把“谁负责落库、谁负责广播、谁负责触发自动化”写清楚。
- 对设备上线触发的附加动作建立统一入口，减少散落调用。

## 重构建议

### 第一优先级：按“主链 + 副作用”拆解处理器

优先针对：

- `telemetry.go`
- `event.go`
- `status.go`

实施方向：

- 保留现有外部构造与启动方式不变。
- 将 payload 解析、身份识别、主存储动作、业务副作用拆成独立 helper。
- 把“失败必须中断主链”和“失败仅记录日志继续”明确区分出来。

预期效果：

- 阅读成本显著下降。
- 修改副作用时不必反复触碰主链。
- 后续更容易补最小范围测试。

### 第二优先级：统一消息契约描述

当前部分文件头已经有中文注释，但还存在描述粒度不一致的问题。建议统一为：

- 文件用途
- 主链输入输出
- 关键副作用
- 失败处理策略
- 兼容性注意事项

预期效果：

- 维护者能更快判断改动影响面。
- 审查时更容易发现“改了 payload，却没同步下游假设”的问题。

### 第三优先级：补流程级文档而不是只补单文件注释

这个目录特别适合继续补“流程图式文档”，例如：

- 遥测消息处理流程
- 状态消息处理流程
- 网关子设备事件处理流程
- 响应消息闭环流程

预期效果：

- 新维护者更容易理解跨文件链路。
- 业务排障时可以更快确定故障落点。

## 维护注意事项

- 不要把新的业务判断直接堆进某个 `*Uplink` 主函数里，优先先问清楚这是不是副作用 helper 的职责。
- 修改任意 payload 解析逻辑前，先确认是否影响存储字段、自动化判断、在线状态和前端展示。
- 修改 `Bus` 或 `UplinkManager` 时，要同步检查关闭语义、初始化顺序和空依赖容错。
- 对网关/子设备场景的处理要单独审查，不要默认它与普通直连设备完全一致。
- 新增日志时优先记录“消息类型、设备标识、关键上下文”，避免只打印模糊错误。
- 如果后续补测试，应优先覆盖消息形态差异、关闭流程和主链/副作用的失败隔离，而不是只测 happy path。

## 建议阅读顺序

第一次阅读这个目录时，建议按下面顺序进入：

1. `uplink_manager.go`
2. `bus.go`
3. `telemetry.go`
4. `event.go`
5. `status.go`
6. `response.go`
7. `device_online.go`

这样的顺序能先建立“框架怎么组织”，再进入“每类消息怎么处理”，最后再理解在线通知等辅助副作用。
