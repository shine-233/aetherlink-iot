## 为什么这条不变式值得单独验证

代码注释里写得很清楚：**进度三列 NULL 表示"从未上报"，与"上报了 0%"是两种事实**。
若导出时把 NULL 写成 0，等于给没有进展的设备凭空记一笔"已开始 0%"——
运维看着导出文件会以为整批都在推进，实际上那台设备可能根本没收到指令。

单测（`fleet_command_job_report_test.go` 的 `KeepsNullDistinctFromZero`）已用结构体覆盖；
本份补的是**数据库往返**：真实写入 `progress_percent` 为 NULL 和 0 的两行，
确认从库里读回来仍然可区分，且 CSV 渲染同样区分。

## 过程中的三个坑

1. **外键 `command_job_details_job_fkey`** —— 直接插明细行报 `23503`，
   必须先插入父作业 `command_jobs`（必填列较多，见测试里的 `seedCommandJob`）。
2. **实例反复 stop/start 会触发 crash recovery** —— 日志出现
   `database system was interrupted` + 长时间 `syncing data directory`，
   且 `postmaster.pid` 残留会阻止再次启动（进程已死时删除它是标准恢复操作）。
3. **C 盘只剩 12GB（98%）时恢复更容易失败** —— 本机磁盘紧张，
   临时实例不宜频繁重启；验证告一段落应停止实例释放资源。

## 边界

1. 仅覆盖 DAL 读取 + CSV 渲染的完整路径；未覆盖超大数据量的 limit 截断行为
   （`CommandJobReportRowLimit` = 50000，构造成本过高）。
2. 单次运行（`-count=1`），未做多轮稳定性验证。
3. 使用的是临时实例上的临时库，未触碰主实例 5432。
