# P0.5 一次性凭证下载 —— 运行期证据

日期：2026-09-12
环境：Windows / go1.26.2 windows-amd64 / PostgreSQL（常驻验证库 `aetherlink_verify`）

## 先说此前到底缺什么

P0.5 门禁要求"**凭证只出现一次**"。此前 ROADMAP 的自评是：

> 一次性凭证下载（"凭证只出现一次"）在代码里没有独立机制，
> 目前只是沿用批量创建的 username 形态，不满足门禁。

但真实缺口比这句更严重：预注册凭证 `devices.voucher` **永久以明文躺在库里**。
创建响应里确实只明文出现一次，但那之后任何人只要能读库、或拿到任意一次导出，
就能**反复**取到明文凭证。也就是说，"只出现一次"从来没真正成立过——
它只在"创建响应"这一条路径上成立，在整条数据生命周期上不成立。

## 本轮实现

| 层 | 文件 |
| --- | --- |
| 迁移 | `backend/sql/95.sql`（建表 + 2 个索引 + 2 条路由的 Casbin 登记） |
| 模型 | `internal/model/device_pre_register_credential_grant.go` |
| DAL | `internal/dal/device_pre_register_credential_grant.go` |
| 服务 | `internal/service/device_preregister_credential_grant.go` |
| HTTP | `internal/api/device_preregister_credentials.go` + `router/apps/device.go` |

端点：

```
POST /api/v1/device/preRegister/credentials/grants          签发一次性下载许可
GET  /api/v1/device/preRegister/credentials/grants/:id/download   下载（消费即失效）
```

## 三条关键设计

1. **"一次"由数据库守，不由应用层的 if 守。** 下载走条件更新
   `WHERE status='pending'` → `consumed`，`RowsAffected=0` 即拒绝。
   应用层即便先查到 pending 也不放行——并发下两个请求都会看到 pending 而双双通过。
2. **一批次同时只能有一个 pending 许可**（部分唯一索引 `…_one_pending_idx`）。
   允许重复签发，就等于可以无限次取到明文，一次性形同虚设。
3. **过期先于消费判定。** pending 但已过期同样拒绝，否则过期时间形同虚设。

## 负向对照

把 DAL 的条件更新从 `WHERE id=? AND tenant_id=? AND status='pending'` 改成
`WHERE id=? AND tenant_id=?`（去掉状态限定）后：

```
device_preregister_credential_grant_test.go:153: concurrent downloads succeeded 8 times, want exactly 1 (got 0 failures)
--- FAIL: TestCredentialGrantConcurrentDownloadOnlyOneWins
```

即 8 个并发请求**全部**拿到了明文——凭证被取走 8 次。还原后恢复 PASS。
这条对照证明并发用例真的在卡"一次"，不是空绿。

## 边界（如实记录）

- **本项不消除 `devices.voucher` 里的明文。** broker 侧 MQTT 基础认证要读它
  （双模式中的 plaintext 分支）。彻底去明文需等 `voucher_hash` 模式全线切换，属另一项。
  本项做到的是：**明文的下发次数被限制为一次且可审计**，不是"库里没有明文"。
- **创建响应里的明文仍在**（既有契约，前端与既有测试依赖）。因此严格讲，
  当前一条凭证的最大明文暴露次数是"创建响应 1 次 + 一次性下载 1 次"。
  要把总数降到 1，需要前端配合在创建流程改为只展示下载入口，属前端改动，未做。
- 无前端界面：签发与下载目前只有接口，没有 UI 入口。
- 未做真实浏览器 E2E（P0.5 门禁里的 file chooser 一项仍缺）。
