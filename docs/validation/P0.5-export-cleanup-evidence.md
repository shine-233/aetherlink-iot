## 做了什么

### 导出（`buildPreRegisterExportRows` / `encodePreRegisterExportCSV`）

- 凭证一律经 `utils.MaskVoucher` 输出，导出面**不含明文**。
- 导出表头为 `device_number,name,voucher_masked,activate_flag,created_at`，
  **刻意区别于导入表头 `device_number,name`**——否则导出文件可被直接回灌，
  用掩码串覆盖真实凭证（掩码串按契约永不落库）。
- 按 `device_number` 升序输出，同一集合多次导出字节一致（可比较、可幂等重放）。
- `created_at` 为空时导出空串，不伪装成 `1970-01-01`。

### 清理分流（`classifyPreRegisterCleanup`）

- **跨租户设备一律 fail closed 返回错误**，不静默过滤：它出现在候选集里说明
  上游查询漏了租户条件，静默跳过会掩盖越权缺陷。
- **已激活（`ActivateFlag != inactive`）设备永不进入可删除集合**，避免清批次时误删在运设备。
- 空批次返回空计划且**不报错**，保证重复调用幂等。

## 2026-09-12 追加：P0.5 接线其实已完成，但漏了 Casbin 登记（已修，提交 38ece31）

核查发现 P0.5 的执行面早已接线，不是"未做"：

- `model.ExportPreRegisterReq` 存在
- `service.ExportDevicePreRegister`（导出，Excel）与 `service.CleanupDevicePreRegister`（清理）已实现
- 路由已挂载：`router/apps/device.go` 的 `GET preRegister/export`、`POST preRegister/cleanup`
- 我的 `classifyPreRegisterCleanup` 被清理服务以注入方式复用（`classify:` 字段），不是死代码

**但 `preRegister/cleanup` 从未写入 `casbin_rule`**。在已迁移库上直接查询确认：

```
select count(*) from casbin_rule where ptype='g2' and v0 like '%preRegister%cleanup%';
--> 0
```

`casbin.route-audit-mode` 默认 **fail-fast**，要求 CasbinRBAC 之后注册的路由必须登记进资源表——
**缺登记会让后端拒绝启动**。同批次的 `preRegister` 与 `preRegister/export` 已在 63.sql 登记，
只有 cleanup 漏了。

修复：新增迁移 `90.sql`（`g2` 资源 + 仅 SYS_ADMIN/TENANT_ADMIN 的 `p` 授权，带 `WHERE NOT EXISTS` 可重跑），
`VERSION_NUMBER` 89 → 90。全新空库实跑：`MIGRATE_OK`，`sys_version = 90`，
`casbin_rule` 中确认出现该路径的 `g2` 与两条 `p` 记录。
