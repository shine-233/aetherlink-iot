## 本次新增：字节上限负向用例

文件：`backend/internal/service/report_run_processor_test.go`
用例：`TestReportGeneratorDetectsByteLimit`

背景：`reportMaxBytes`（25 MiB）与 `errReportByteLimit` 已在 `report_run_processor.go` 实现，
`reportLimitedBuffer` 会在写入超限时报错并分类为 `byte_limit_exceeded`，
但全仓检索 `*_test.go` 无任何一处引用 `errReportByteLimit` / `reportLimitedBuffer` / `reportMaxBytes`。
即字节上限属于"已实现、零覆盖"——一旦回归，可能静默产出被截断的报表却仍返回成功码。

构造方式：单 device/key 最多只能产出 `reportMaxRows`（100000）行，
因此每行值取 512 字节，使 CSV 在触发行上限之前先越过 25 MiB 字节上限；
行数取 `limit-1` 以恰好停在行上限、不越过，确保断言落在字节上限路径上。

断言强度：`err != nil && code == "byte_limit_exceeded" && payload == nil`。
断言的是具体错误码而非"是否出错"，因此该用例只能由字节上限路径满足，
不会因为行上限、遥测失败或 CSV 写失败而假通过。

结果：


回归确认（新增后重跑，全部 ok）：

## 覆盖率扫描发现的另外两个 0% 缺口（已修复）

用 `go test -coverprofile` 做系统性核查（而非逐个猜），发现 `report_run_processor.go`
里还有两个函数覆盖率为 **0.0%**，且都属于 P0.6 关键路径：

| 函数 | 修复前 | 修复后 | 为何重要 |
| --- | --- | --- | --- |
| `DeliverClaim` | 0.0% | **100.0%** | SMTP outcome → 结算动作的映射，即"ambiguous 入账"契约本身 |
| `isReportClaimLost` | 0.0% | **100.0%** | lease 丢失判定，fencing 的判定入口 |

### `DeliverClaim` 为何 0%：结算动作硬编码，无法注入

原实现直接调用 `dal.SettleReportDeliveryAccepted` / `dal.RetryClaimedReportDelivery` /
`dal.SettleReportDeliveryAmbiguous`，无注入点，因此任何单元测试都会打到数据库。

**真正的风险不是"没测"，而是映射本身无保护**：
`switch` 的 `default` 分支把"既非确定成功、也非确定失败"归为 ambiguous。
若有人误将其改成 accepted，单元层不会有任何反应 —— 一封**可能没发出去**的邮件
会被记成投递成功。这正是 ROADMAP P0.6「前端必须独立呈现 SMTP 风险」所依赖的判定。

### 修复方式：沿用同文件既有模式，生产行为不变

`GenerateClaim` 早已用可注入字段（`RetryGeneration`/`FailGeneration`/`CompleteGeneration`）
+ nil 回退到 `dal.*` 的写法。对投递侧做同样处理：
新增 `SettleDeliveryAccepted` / `SettleDeliveryAmbiguous` / `SettleDeliveryFailed` /
`RetryDelivery` 四个字段，`NewReportRunProcessor` 中仍指向原 `dal.*` 函数，
并配套 `settleDeliveryAccepted()` 等访问器保持 nil 回退。

**因此生产路径行为完全不变**（字段非 nil 时指向的就是原来那些函数），
只是让结算映射变得可测。

### 新增用例

- `TestDeliverClaimMapsSMTPOutcomeToSettlement`（6 个子用例，表驱动）
  accepted→accepted、failed→retry（带 code）、ambiguous→ambiguous、
  **未识别 outcome→ambiguous 而非成功**、invalid envelope→failed/invalid_envelope、
  SMTP 缺失→retry/smtp_not_configured
- `TestDeliverClaimRejectsIncompleteClaimWithoutSettling`
  残缺 claim 不得结算（否则把畸形 claim 伪装成投递失败）
- `TestIsReportClaimLostRecognisesWrappedFenceLoss`
  判定须穿透 `fmt.Errorf("%w")` 包装，否则任一加上下文的 helper 都会击穿 fencing

### 关于 `csv_write_failed`（66.7%，**故意不补**）

经核查该分支**不可达**：`reportLimitedBuffer.Write` 只可能返回 `errReportByteLimit`
或委托 `bytes.Buffer.Write`（永不报错），`csv.Writer` 的错误仅来自底层 writer。
故 `reportWriteErrorCode` 的 `csv_write_failed` 是纯防御性回退。
**不为凑覆盖率而构造假测试**——这是结论，不是遗漏。

## 状态口径

本文档区分三种状态，不得混用：

- **PASS（已运行）** —— 本机实跑通过，可引为证据
- **SKIP（已实现，未运行）** —— 代码存在但被环境门禁跳过，**不得**引为通过
- **pending（未产出）** —— 尚无任何运行记录

按此口径：

- **P0.7 密码层** = PASS（`pkg/secrets` 8/8）
- **P0.6 生成语义** = PASS（遥测失败、行上限、字节上限、信封分类）
- **P0.6 投递结算映射** = PASS（`DeliverClaim` 0%→100%，含 ambiguous 不得记为成功）
- **P0.6 lease 丢失判定** = PASS（`isReportClaimLost` 0%→100%，穿透错误包装）
- **P0.6 并发 / fencing 争用 / outbox 原子性** = **SKIP**
  （`TestReportMigration83Postgres` 的 competing materializers/claimers、stale fence、
  expired owner、outbox 原子性——需真实 PostgreSQL 的**并发**语义，单元层无法替代）
- **P0.6 端到端与前端** = pending（需运行中的平台）

**P0.6 整体仍 `done=false`。** 本次修复把"服务层可测的部分"补齐了，
但**并发**争用与 fenced 事务的原子性只有在真实 PostgreSQL 上才成立——
用服务层单测去替代它们，正是 ROADMAP §4 所禁止的"以单元测试绿色宣称完成"。
