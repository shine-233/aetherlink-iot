# P1.5 / P1.6 死代码核查（2026-09-12）

方法：与 `P2-P3-audit.md` 同一套 —— 不读 ROADMAP 的"实现状态"文字下结论，一律以
**grep 调用点 + 编译** 为准。

判据：

1. **有没有消费方** —— 函数存在但全库无调用，等于不存在。
2. **判调用方时必须排除定义文件自身与 `_test.go`** —— 只被单测调用的函数，
   在生产链路里同样等于不存在；单测绿证明的是"函数按作者预期工作"，不是"能力已上线"。

本机环境：无 Docker、无网络、无真实 PostgreSQL。需要运行期的证据一律标记为 pending。

## P1.5 边缘运维

ROADMAP 交付物：节点注册/证书、心跳健康、版本兼容、配置/模板/规则下发状态、
冲突解决、远程升级和回滚。

### 唯一的接线点

```
internal/service/edge_sync.go:106
  CreateEdgeSync → DetectEdgeSyncConflict(pending, req.ResourceType, req.ResourceID, content)
```

`DetectEdgeSyncConflict` 是全库唯一被生产代码调用的治理函数。冲突闸门在落库前执行，
命中即返回带 `conflict=true` 的错误——这部分是真实生效的。

### 两个死函数

`ClassifyEdgeNodeHealth`（`edge_governance.go:50`）与
`CheckEdgeVersionCompatibility`（`edge_governance.go:70`）除定义与
`edge_governance_test.go` 外**零调用方**。

后果（比"少个功能"更具体）：

- 门禁要求"节点离线产生告警" —— 健康判定函数无人调用，**不存在任何路径会得出
  offline/degraded/unknown 的结论**，告警无从触发。
- 门禁要求"重连后按版本同步""无法判断兼容就不允许下发" —— 版本兼容函数无人调用，
  **下发前没有任何兼容性检查**。

### 结构性缺口（决定了上面两项无法靠补调用修好）

- `backend/sql/` 全库**无 `edge_nodes` 表**；`EdgeNode` 类型只存在于死包
  `internal/roadmap/types.go:91`。
- 注册/心跳接口在 `internal/roadmap/contracts.go:35-36`，实现是
  `internal/roadmap/skeletons.go:50-51` 的 `UnwiredEdgeOperations` → `ErrNotImplemented`。
  该包除自身外零 import（见 `P2-P3-audit.md`）。
- `edgeSyncPayload.Version` 恒为 1（快照格式版本），**没有同步修订号**，
  因此"边缘已拿到哪一版"这个前提数据根本不存在。

判定：**pending**。不是"补个调用就能点亮"——健康与版本兼容都依赖一个尚不存在的
节点注册表与同步修订号。先做节点注册，再谈这两个函数的接线。

## P1.6 模板市场产品化

ROADMAP 交付物：浏览/搜索/行业打包下载、导入冲突预览、签名、依赖检查、升级/回滚和审计。

### 唯一的接线点

```
internal/service/device_template_market.go:58
  ExportMarketBundle → SignMarketBundle(bundle)
```

出包即签名，未配置密钥拒绝出包——这是真实生效的行为变更，且已按 P0.7 的口径 fail closed。

### 三个死函数

`VerifyMarketBundle`、`CheckMarketBundleDependencies`、`PreviewMarketBundleImport`
除定义与 `device_template_market_integrity_test.go` 外**零调用方**。

根因：**没有导入打包载荷的接口**。市场路由只有三条：

```
router/apps/device.go:163  GET  market/catalog
router/apps/device.go:164  GET  market/bundle
router/apps/device.go:183  GET  market/detail/:market_id
```

没有 POST 导入端点，因此"验签 → 依赖检查 → 冲突预览"这条链路**没有入口**。
ROADMAP 自述的"导入接口本身尚未接入打包载荷"是准确的，但 §1.2 的校准句
「模板市场**签名与依赖检查已实现**」会让人误判依赖检查可用——它只有函数，没有入口。

后果：

- 门禁"坏签名拒绝" —— 无导入端点，**坏包根本进不来，也验不了**。
- 门禁"导入不产生孤儿租户数据" —— 无导入路径，该风险当前不发生（也没有被防护）。
- 门禁"升级可回滚" —— 未做（需版本与快照，待排迁移）。
- 门禁"所有动作有审计记录" —— 未做。

判定：**partial**（签名侧真实生效）。验签/依赖/预览要真正可用，必须先有导入端点。

## 建议的处置顺序

1. **P1.6 先补导入端点**（POST market/bundle/import），把验签 → 依赖检查 → 冲突预览
   串成一条真实链路。这是三者中唯一"只差入口"的，成本最低、收益最直接。
2. **P1.5 先做节点注册**（`edge_nodes` 表 + 注册/心跳端点 + 同步修订号），
   再接线健康与版本兼容。反过来做只会得到一个没有数据来源的判定函数。
3. 两者新增端点都必须登记 Casbin，并由
   `router/apps/casbin_route_registration_contract_test.go` 守住
   （该用例在 `casbin.route-audit-mode: fail-fast` 下等价于启动门禁）。
4. `internal/roadmap` 死包的处理见 `P2-P3-audit.md`；P1.5 的 `EdgeNode` 定义也在其中，
   删除该包前需先把它搬走或另行落表。
