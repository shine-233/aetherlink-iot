# 高级表格操作组件

## 目录职责

`frontend/src/components/advanced` 保存前端里偏“表格增强交互”的通用组件，主要服务于列表页头部操作、列显隐配置和拖拽排序这类高频管理台交互。

这些组件本身不直接承载业务接口调用，但会成为大量列表页的共同交互入口，因此契约稳定性和可复用性都很重要。

## 文件关系

- `table-header-operation.vue`
  - 提供新增、批量删除、刷新、列设置等表头操作入口，通常由各类管理页直接挂载。
- `table-column-setting.vue`
  - 提供列显隐勾选和拖拽排序能力，通常作为 `table-header-operation.vue` 的配套增强组件使用。

## 重点文件

- `table-header-operation.vue`
  - 目录级主入口，负责把表头操作事件透传给外层页面。
- `table-column-setting.vue`
  - 负责列配置的本地交互状态与拖拽排序结果回写。

## 当前静态审查结论

- 问题：这两个组件都很轻，但会被大量列表页复用，一旦 `props / emits / v-model` 契约漂移，回归面会很大。
- 问题：`table-column-setting.vue` 直接操作 `FilteredColumn[]`，如果列模型后续继续扩张，组件可能逐步承担过多列配置语义。
- 问题：`table-header-operation.vue` 当前更像事件转发层，如果后续继续往里叠加权限判断、批量状态展示或接口调用，容易从“通用表头”滑向“业务特化组件”。

## 改进方案

- 继续保持这两个组件只负责交互编排与事件透传，不直接耦合业务 service。
- 为列模型、事件载荷和按钮开关补更明确的注释和类型说明，降低跨页面复用时的误用风险。
- 后续若出现更多表头动作，优先用插槽或配置扩展，而不是把业务判断硬塞进当前组件。

## 建议实施步骤

1. 先补齐文件头、`props` / `emits` / `v-model` 注释，明确输入输出边界。
2. 再梳理哪些表头动作是真正通用的，哪些应该回到业务页面自身处理。
3. 后续如果列配置模型继续膨胀，再考虑把拖拽、显隐、分组等能力拆成更细粒度的 helper 或子组件。

## 预期效果

- 管理台列表页的共用交互入口更容易理解和复用。
- 后续接手者更容易判断问题出在通用组件层还是业务页面层。
- GitHub 浏览项目时，这个目录的定位会比“泛泛的高级组件”更清楚。
