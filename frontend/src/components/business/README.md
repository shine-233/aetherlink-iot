# 业务通用组件

## 目录职责

`frontend/src/components/business` 保存跨页面复用、但又带有明确业务语义的组件。既包含纯交互组件，也包含为多个业务页面统一 API 和状态语义的自包含管理器。

## 文件关系

- `login-agreement.vue`
  - 登录与注册等入口页复用的协议确认组件，负责勾选状态同步和协议/隐私链接点击事件抛出。
- `email-template-manager.vue`
  - 系统通知配置页与租户告警通知组页复用的告警邮件模板管理器，负责分页、CRUD、预览、默认切换和用户反馈；作用域不由组件传参，而由后端登录 claims 判定。

## 重点文件

- `login-agreement.vue`
  - 当前目录最核心的业务组件，直接影响登录前的合规交互和表单提交前置条件。
- `email-template-manager.vue`
  - 直接影响告警邮件正文，但不负责 SMTP 配置、收件人选择或真正发送；允许变量、纯文本限制和系统/租户隔离均以后端合同为准。

## 当前静态审查结论

- 问题：该组件看起来很轻，但实际处于登录入口链路，`value` 默认值、协议链接默认地址和点击事件语义都属于敏感契约。
- 问题：如果后续在组件内部继续叠加“是否必选”“国际化文案拼装”“平台差异链接”之类逻辑，容易让它从展示组件变成合规策略组件。
- 问题：默认地址 `/terms` 和 `/privacy` 目前是静态值，若未来存在多租户品牌化或外链协议页，这里可能成为隐蔽的配置漂移点。
- 问题：邮件模板管理器同时出现在系统和租户页面，若在前端增加可选 `tenant_id`，会破坏后端 claims 作用域边界；复用时应保持零作用域参数。
- 问题：模板预览成功不等于 SMTP 投递或告警发送成功，页面文案和进度报告不能把预览证据外推为运行验收。

## 改进方案

- 保持组件只负责“勾选 + 文案 + 点击事件”，不要把真正的登录校验策略塞进组件内部。
- 对默认协议地址、默认勾选值和事件契约补更清晰的中文说明，降低接入页误用风险。
- 如果后续协议地址存在环境差异，优先把默认值提升到配置层或页面层注入。
- 邮件模板变量扩展应先修改后端白名单和渲染限制，再同步 API 类型、四语言文案和共享组件，不要只在前端展示新变量。

## 建议实施步骤

1. 先补齐文件头和 `props / emits / computed` 注释，明确该组件不是策略判定层。
2. 再梳理哪些页面必须显式传入协议链接，哪些可以复用默认值。
3. 如后续接入品牌化或多站点协议页，再把链接默认值抽到统一配置。

## 预期效果

- 登录入口链路里的协议勾选组件更清晰、可维护。
- 后续新增登录/注册页面时更容易正确复用。
- GitHub 浏览项目时，这个目录不会再显得过于抽象。

## 验证建议

静态改动先核对两个挂载页面、API wrapper、四语言 key 和后端权限/变量白名单；允许执行验证时，再运行本目录 targeted ESLint/Vitest，无需先做 broad build/test。
