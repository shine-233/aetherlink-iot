# grid/components 组件说明

## 目录职责

本目录保存网格布局的局部 Vue 渲染组件，负责把增强网格状态转换为可视化节点、拖放提示和网格项内容容器。

它位于 `common/grid` 目录内部，关注点是“渲染层拆分”而不是“布局数据编排”。如果上层需要改布局协议、事件命名或业务组件接入方式，通常会先影响这里，再向外扩散。

## 文件关系

- `GridCore.vue` 直接适配 `grid-layout-plus` 的 `GridLayout` 与 `GridItem`，是布局渲染和事件转发中心。
- `GridItemContent.vue` 包装单个网格项，处理标题、只读状态、组件动态渲染和默认插槽。
- `GridDropZone.vue` 提供拖拽进入网格时的投放提示与可视反馈。
- `index.ts` 汇总导出本目录组件，供上层网格入口统一引用。

## 组件协作链路

1. 上层容器把 `layout`、`config` 和只读状态传给 `GridCore.vue`。
2. `GridCore.vue` 把布局副本交给 `grid-layout-plus`，并为每个布局项创建 `GridItem`。
3. 每个 `GridItem` 内部再交给 `GridItemContent.vue`，决定标题区域、插槽回退和内容容器样式。
4. 需要外部拖放提示时，由上层决定是否挂载 `GridDropZone.vue`，它只回传拖放事件，不直接改布局。
5. 其他模块应优先通过 `index.ts` 导入，避免对具体文件路径形成硬编码依赖。

## 重点文件

- `GridCore.vue`：核心渲染层，事件参数和双向布局同步最容易影响外部页面。
- `GridItemContent.vue`：网格项内容容器，需关注插槽回退和动态组件 props 透传。
- `GridDropZone.vue`：拖放状态展示，需与外部拖拽流程保持状态语义一致。

## 静态审查要点

- 检查 `GridCore.vue` 是否同时承担“事件转发”和“业务决策”；如果开始混入业务判断，后续排查拖拽问题会变得困难。
- 检查 `internalLayout` 与 `props.layout` 的同步方式；凡是直接共享引用的修改，都可能破坏 Vue 单向数据流和上层状态追踪。
- 检查 `GridItem` 上的拖拽、缩放、容器变化事件参数顺序；这类顺序一旦变化，TypeScript 未必能完全拦住运行时回归。
- 检查 `GridItemContent.vue` 的插槽约定是否稳定；业务方一般默认能拿到完整 `item`，删改字段会造成静默行为变化。
- 检查 `GridDropZone.vue` 是否只维护视觉状态；如果把投放结果、布局写回或异步副作用塞进来，会让职责边界变模糊。
- 检查 `index.ts` 是否覆盖全部真实组件；目录新增文件但未导出时，调用方容易绕过公共入口直接引用内部实现。

## 审查建议

- 修改 `GridCore.vue` 事件时，必须确认 `GridLayoutPlus.vue` 的事件转发和测试仍匹配。
- 动态组件渲染应避免吞掉 props 或 slot，防止业务组件在网格中表现不一致。
- 拖放视觉状态只应表达当前交互，不应在组件内持久化业务布局。

## 重构建议

- `GridCore.vue` 可以把重复的事件转发器收敛为映射表或工厂函数，减少样板代码并降低漏改风险。
- `GridCore.vue` 里 `GridItem` 模板参数较多，后续可评估抽出“布局项适配层”以压缩模板密度。
- `GridItemContent.vue` 目前承担容器壳子和默认展示逻辑，若后续接入更多标题操作区，可拆出头部子组件。
- `GridDropZone.vue` 的提示文案、颜色 token 与交互态可以进一步配置化，方便主题系统和无障碍适配。
- `index.ts` 目前既像 barrel file 又像元信息清单；如果后续元数据继续增长，建议拆成独立常量文件。
