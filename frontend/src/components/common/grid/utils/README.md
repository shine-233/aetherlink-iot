# `grid/utils` 目录说明

## 功能定位

这个子目录承接 `common/grid` 体系里的纯工具层，主要为上层 grid 组件、hooks 和聚合工具提供无状态或低状态的辅助能力。职责可以概括为 5 类：

1. 布局输入校验：拦截非法坐标、尺寸、断点配置和大网格风险。
2. 布局算法：寻找可放置位置、碰撞检测、纵向压缩与拖拽后的连锁推挤。
3. 响应式转换：根据断点和列数派生多套布局，并处理媒体查询监听。
4. 性能辅助：节流、防抖、轻量缓存、异步串并发控制、运行期耗时采样。
5. 通用基础函数：克隆、统计、几何换算、像素映射和展示格式化。

这里更偏“被复用的实现细节层”，不负责组件渲染，也不直接承载业务规则。

## 文件关系

- `index.ts`
  统一导出门面。上层若只关心能力入口，通常从这里引入。
- `validation.ts`
  输入防线。为布局算法和响应式转换提供前置合法性检查。
- `layout-algorithm.ts`
  位置搜索、碰撞检测、紧凑化、重叠面积计算等核心布局算法。
- `responsive.ts`
  从基础布局派生断点布局，并提供断点信息推导与媒体查询封装。
- `performance.ts`
  为拖拽、缩放、重排等高频交互提供性能保护与监控辅助。
- `common.ts`
  提供通用克隆、统计、网格与像素换算、背景样式生成、格式化等基础函数。

依赖方向大致如下：

- `validation.ts` 相对独立，可被其余模块直接复用。
- `layout-algorithm.ts` 自带内部克隆与碰撞逻辑，和 `validation.ts` 在职责上互补，但当前没有深度复用。
- `responsive.ts` 偏向布局派生规则，理论上可与 `layout-algorithm.ts` 联动，但当前只做比例缩放和边界修正。
- `performance.ts` 与其余模块耦合最低，主要通过数据结构约定服务上层。
- `common.ts` 是最通用的一层，适合作为其他模块的基础配套。

## 静态审查要点

- `layout-algorithm.ts`
  `moveItemWithCollisionHandling` 是复杂度最高的实现，混合了坐标归一化、BFS 推挤和紧凑化，后续改动最容易引入拖拽回归。
- `layout-algorithm.ts`
  多处碰撞判断逻辑以内联形式重复出现，若未来修正规则，需确认所有实现点是否同步。
- `responsive.ts`
  断点转换目前主要按列数比例缩放横向尺寸，纵向只做启发式保底，高度与布局意图保持并不完全等价。
- `validation.ts`
  返回值是“发现第一个错误即返回”，适合快速拦截，但不利于批量展示多条问题。
- `performance.ts`
  性能监控同时兼容 `Performance API` 和时间戳兜底，属于运行环境敏感区，后续改动要注意 SSR、测试环境和浏览器能力差异。
- `common.ts`
  统计类函数产出的“fragmentation / compactness / balance”偏启发式，适合做对比与调试，不应被当作业务真值。

## 重构建议

- 提炼统一的碰撞判定原语
  现在 `layout-algorithm.ts` 里有多处矩形重叠判断，建议收敛为同一套底层函数，避免规则漂移。
- 拆分 `moveItemWithCollisionHandling`
  可拆为“坐标归一化”“碰撞传播”“静态项回退决策”“压缩收尾”几个独立纯函数，降低阅读成本。
- 为响应式转换补齐规则文档
  当前 `responsive.ts` 更像经验型策略集合，建议把“小屏强制满宽/半宽/最小高度”的设计意图写成明确约束。
- 把统计指标和展示格式化从 `common.ts` 分层
  一部分是布局分析，一部分是 UI 展示辅助，后续拆分后更利于查找和测试。
- 统一校验错误模型
  `validation.ts` 可以逐步引入稳定错误码，而不是仅依赖自由文本消息，方便 UI 做本地化和自动修复提示。
- 评估 `index.ts` 的命名门面策略
  如果上层已经有更大的聚合入口，可考虑在这里减少别名导出，避免来源不清。
