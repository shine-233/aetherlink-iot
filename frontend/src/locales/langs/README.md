# 多语言资源目录

## 目录职责

本目录按语言保存前端界面的 i18n 文案资源，供 `frontend/src/locales` 的语言加载逻辑按当前语言环境读取。每个子目录代表一种语言包，例如 `zh-cn`、`en-us`、`es-es`、`fr-fr`。

## 文件关系

- `zh-cn/`：中文语言包，通常作为业务语义和键名对照的主要参考。
- `en-us/`：英文语言包，用于英文界面展示和跨语言键值校验。
- `es-es/`：西班牙语语言包，应与中文、英文保持相同 JSON 文件集合和键路径。
- `fr-fr/`：法语语言包，应与其他语言包保持同构，避免缺键导致页面回退或展示原始 key。

各语言目录下的 JSON 文件按业务域拆分，例如 `common.json` 存放通用文案，`device_template.json` 存放物模型相关文案，`visual-editor.json` 存放可视化编辑器相关文案。新增页面文案时，应优先放入对应业务域文件，而不是集中塞入通用文件。

## 重点文件

- `common.json`：跨模块通用按钮、提示、状态文案，修改影响范围最大。
- `route.json`：路由标题和菜单展示文案，需与前端路由配置保持一致。
- `device_template.json`：物模型页面文案，需与物模型表单、测试和校验逻辑同步维护。
- `visual-editor.json`：可视化编辑器文案，需注意嵌入式面板场景下的展示长度。
- `rdi.json`：RDI 相关界面文案，涉及外部业务术语时应以产品文档为准。

## 审查建议

- 问题描述：多语言 JSON 文件数量较多，人工新增文案时容易只改一个语言包，造成其他语言缺键。
- 改进方案：增加语言包键路径一致性检查脚本，至少校验文件集合、顶层 key、嵌套 key 是否一致。
- 实施步骤：以 `zh-cn` 或产品指定基准语言为源，递归读取全部 JSON key；再逐语言对比差异并在 CI 中失败提示。
- 预期效果：提前发现缺失翻译、重复 key 和结构漂移，减少运行时显示原始翻译 key 的风险。

## 使用注意

- 不要在不了解语境的情况下直接机器翻译并提交业务文案，尤其是设备、告警、自动化和 RDI 术语。
- 修改 JSON 时保持合法格式，避免尾逗号、重复 key 和不可见控制字符。
- 删除文案前应先搜索调用方，确认页面、组件、测试和自动化脚本均不再引用。
