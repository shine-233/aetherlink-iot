# 前端状态模块目录说明

## 目录定位

`frontend/src/store/modules` 是前端 Pinia 状态中心，负责承接“跨页面、跨路由、跨组件”的共享状态，而不是页面私有临时变量。这里的模块覆盖了登录态、动态路由、应用壳层、主题系统、标签页、设备详情上下文，以及可视化编辑器运行时状态，是前端业务编排最密集的目录之一。

从真实结构看，这个目录已经形成两类模块：

- 通用壳层模块：`app`、`auth`、`route`、`tab`、`theme`、`sys-setting`
- 业务能力模块：`device`、`visual-editor`、`editor.ts`、`widget.ts`

这意味着它既承担“系统初始化骨架”，也承担“业务编辑器状态容器”。后续维护时要特别避免把页面局部逻辑继续堆进 store，导致状态边界越来越模糊。

## 真实结构概览

| 路径 | 主要职责 | 关联模块 |
| --- | --- | --- |
| `app/index.ts` | 管理应用壳层状态、页面刷新、布局监听、标题同步等全局行为 | `theme`、`route`、`tab`、`auth` |
| `auth/index.ts` | 管理 token、登录登出、用户信息恢复、密码策略提示与会话清理 | `route`、`tab`、登录接口 |
| `auth/shared.ts` | 存放认证相关辅助逻辑，适合沉淀纯函数 | `auth/index.ts` |
| `route/index.ts` | 动态路由初始化、菜单、缓存路由、面包屑、授权导航 | `auth`、`tab`、Vue Router |
| `route/shared.ts` | 路由过滤、菜单转换、排序、缓存信息组装等纯转换逻辑 | `route/index.ts` |
| `tab/index.ts` | 标签页生命周期、页面缓存协同、路由切换后的页签状态 | `route`、`app` |
| `tab/shared.ts` | 标签页计算和转换辅助逻辑 | `tab/index.ts` |
| `theme/index.ts` | 主题模式、主题色、Naive UI token、持久化主题设置 | `app`、`sys-setting` |
| `theme/shared.ts` | 主题变量计算、样式映射和持久化辅助逻辑 | `theme/index.ts` |

| `editor.ts` | 轻量级编辑器状态入口，适合作为老链路兼容层 | 可视化编辑器相关页面 |
| `widget.ts` | 组件/控件选择与运行时轻状态 | 编辑器或卡片配置流程 |

## 模块关系与关键链路

### 1. 登录到页面可用的初始化链路

最关键的系统链路是 `auth -> route -> tab -> app`：

- `auth` 在登录成功或刷新恢复时写入 token、用户信息，并触发权限相关初始化。
- `route` 根据认证结果、后端返回路由和前端静态路由生成最终可访问导航结构。
- `tab` 根据当前路由状态维护标签页、缓存页和关闭策略。
- `app` 再把这些状态挂接到页面壳层，例如标题、刷新行为、布局响应和全局开关。

这条链路的核心风险不是单个 store 写错，而是“初始化顺序”和“失败后的清理顺序”错位。因此任何一个模块新增副作用，都要考虑页面刷新、token 失效、退出登录和用户信息缺失时会不会把其他 store 留在脏状态。

### 2. 视觉与品牌配置链路

`theme` 与 `sys-setting` 共同决定前端最终呈现：

- `theme` 偏本地主题模型与 Naive UI token
- `sys-setting` 偏后端配置、品牌资源、系统级开关

这两个模块如果同时修改颜色、背景、Logo、暗色模式或 CSS 变量，很容易出现“本地持久化值覆盖后端设置”或者“后端设置下发后没有同步刷新 UI”的问题。相关变更应优先梳理状态源头，避免双向覆盖。

### 3. 编辑器运行态链路

`editor.ts`、`widget.ts` 与 `visual-editor/*` 明显处于新旧两代状态模型并存阶段：

- `visual-editor/*` 更像统一能力层，已经拆出适配、配置服务和数据流管理。
- `editor.ts`、`widget.ts` 更像轻量兼容层，可能仍被部分旧页面直接引用。

这类结构通常意味着项目正在从“页面直控状态”迁移到“统一编辑器状态中心”。继续开发编辑器功能时，优先落在 `visual-editor/*` 内，而不是继续扩写 `editor.ts` 和 `widget.ts`。

## 重点文件阅读建议

- `auth/index.ts`
  登录、登出、会话恢复和用户信息刷新主入口。涉及加密登录、token 存储、密码策略提示、第三方 token 清理等副作用，是最需要稳态处理的 store。
- `route/index.ts`
  动态路由装配中枢。和权限、菜单、缓存页、面包屑、导航守卫强相关，适合优先审查初始化时序和错误降级。
- `route/shared.ts`
  这里适合沉淀所有“可纯函数化”的路由转换逻辑，是后续提高可测性的最佳切入点。
- `app/index.ts`
  更偏应用壳层协调器。若后续发现它越来越像“全局杂物箱”，就说明需要继续拆分。
- `theme/index.ts` 与 `theme/shared.ts`
  建议将“主题状态”和“主题推导逻辑”继续分层，避免 UI token、持久化和页面副作用混在一起。
- `visual-editor/*`
  这是最像“子系统”的一组 store 文件，已经具备服务层、适配层、运行态管理层的雏形，适合单独治理。

## 维护注意事项

- 不要把页面局部状态直接塞进这里。能留在页面 `setup` 内部的，就不要提升为全局 store。
- 涉及跨 store 调用时，先明确“谁拥有状态、谁只消费状态”，避免互相写值形成隐式循环依赖。
- 新增异步 action 时，优先确认首屏加载、刷新恢复、退出登录三种场景下是否需要显式 reset。
- 需要持久化的字段要明确来源和优先级，避免本地缓存与后端配置互相覆盖。
- 路由、标签页、主题这三类模块一旦改动，最容易引出“页面可打开但状态错乱”的隐性问题，维护时应优先做静态链路审查。
- `visual-editor/__tests__` 已经存在，说明编辑器状态层具备补强单测的基础。后续如果继续重构，应优先保护这部分能力，不要回退成只能靠页面联调验证。

## 建议的重构方向

### 1. 继续把纯逻辑从 store action 中剥离

目前 `route/shared.ts`、`theme/shared.ts`、`tab/shared.ts` 已经证明这种模式可行。建议把 `auth`、`app`、`sys-setting` 中可纯函数化的状态整理、字段归一化、默认值合并逻辑继续下沉到 helper 或 shared 文件中。

预期效果：

- store 只负责协调副作用与提交状态，阅读成本更低
- 更容易补单测
- 异步失败与边界情况更容易复用降级逻辑

### 2. 明确新旧编辑器状态边界

`visual-editor/*` 与 `editor.ts`、`widget.ts` 并存，说明存在迁移中的双轨结构。建议梳理真实调用方，逐步把新功能统一收口到 `visual-editor`，把旧文件降为适配层或明确退役对象。

预期效果：

- 减少编辑器功能散落多个 store 的维护成本
- 降低新旧卡片模型共存带来的认知负担
- 为后续抽离独立编辑器子模块创造条件

### 3. 给全局初始化链路补“失败态设计”

当前系统 store 已经不是简单数据仓库，而是启动编排器。建议对 `auth -> route -> tab -> app` 的关键动作补一份失败态梳理，包括 token 失效、后端路由字段缺失、用户信息不完整、退出登录中断等场景。

预期效果：

- 降低首屏偶发白屏或导航错乱概率
- 后续接入更多权限、租户或品牌配置时更稳
- README 与代码行为更一致，便于新维护者快速接手
