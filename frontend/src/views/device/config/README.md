# 设备配置入口页

## 目录职责

`frontend/src/views/device/config` 负责设备配置入口、配置列表、物模型市场选择、配置创建/编辑以及配置发布相关流程。

它处于“设备配置域”的上游入口层，既要承接配置列表和筛选，又要协调物模型市场登录态和发布确认流程，因此属于设备配置链路里的核心壳层。

## 文件关系

- `index.vue`
  - 设备配置入口和列表页，负责配置列表、入口操作和详情跳转。
- `modules/*`
  - 提供物模型市场、登录、发布确认和配置编辑弹窗等子流程。
- `composables/use-market-auth.ts`
  - 管理市场认证状态和相关前端协作逻辑。

## 重点文件

- `index.vue`
  - 配置列表、入口跳转和页面级状态协调中心。
- `modules/config-modal.vue`
  - 配置创建/编辑弹窗，通常涉及配置基础字段和回填逻辑。
- `modules/market-login-modal.vue`
  - 市场登录补充弹窗，负责市场 token 获取与上层继续动作的衔接。
- `modules/publish-confirm-modal.vue`
  - 配置发布确认流程，关系到配置发布语义和用户可见确认链路。

## 设备配置主页面组静态审查记录

### config-modal.vue

- 该弹窗同时承载“新增”和“编辑”两种语义，标题切换、提交分支和关闭事件都集中在同一组件内，后续继续加字段时容易把状态判断摊得更散。
- 组件内部目前能看到“新增态默认值”和“关闭后复位”，但看不到编辑态数据回填来源；后续若排查编辑问题，建议优先追父层传值与弹窗打开时机。
- 模板选项在每次打开弹窗时都会重新拉取，适合保证新鲜度，但如果模板数量继续增长，后续要一起审视分页、缓存和下拉滚动补数策略。
- `submitted` 事件目前从静态代码看更接近“提交流程结束”而不是严格的“保存成功”，如果上层把它当成功信号使用，建议统一约定事件语义。

### market-login-modal.vue

- 组件职责比较单纯，只负责拿到市场 token 并把继续动作交还给父层，这个边界本次已在注释中明确。
- 登录响应兼容了 `res.token` 和 `res.data.token` 两种形状，说明接口封装层存在历史兼容包袱，适合后续下沉到服务层统一。
- 错误提示依赖请求层拦截器统一兜底，当前组件保持静默；如果以后替换请求库或重构拦截器，这个依赖点需要同步回归。
- 注册地址由当前 `origin` 推导到 `:18083/register`，这是明显的部署假设，适合后续提炼成集中配置。

## 当前静态审查结论

### 发现的问题

- 物模型市场登录态、配置创建/编辑和发布确认都聚集在同一目录，容易把多个状态机耦合在一起。
- 设备配置入口页既是列表入口，又连接物模型市场和详情链路，后续功能扩张时容易继续变厚。
- 配置弹窗与市场登录弹窗的职责边界之前缺少就地说明，不利于协作时快速判断改动风险。
- README 之前信息量偏少，不足以让维护者快速判断哪些模块属于高风险改动面。

### 改进方案

- 继续补齐核心文件头和目录 README，把市场登录态、配置发布和配置回填的边界说明清楚。
- 逐步把市场认证状态、发布确认状态机和配置 payload 构造逻辑收敛成更可解释的 helper 或 composable。
- 将部署假设类逻辑（如市场注册页地址推导）收口到配置层或统一 helper，减少页面内散落约定。
- 保持入口页与配置详情页 README 之间的表述一致，形成设备配置域的完整导航链。

### 建议实施步骤

1. 先完成入口页和关键弹窗文件的中文注释与静态审查建议补齐。
2. 再识别市场认证、配置发布和详情跳转中的重复状态逻辑，逐步抽取 helper。
3. 静态批次结束后，再统一验证登录态、发布确认和配置跳转链路。

### 预期效果

- 设备配置入口链路更容易维护，新增市场或发布逻辑时更容易判断改动落点。
- GitHub 浏览者能从 README 快速看懂“入口页 -> 配置详情 -> 子模块”的关系。
- 后续补测试或统一验证时，更容易按模块拆分风险面。
