# 设备 / 子设备详情

## 目录职责

本目录承载 `frontend/src/views/device/details-child` 范围内的设备详情页与其局部业务编排，主要负责路由入参解析、详情拉取、tab 组织、在线状态展示和编辑入口。

## 文件关系

- `index.vue`：本目录的主页面文件，承载详情展示、编辑弹窗、状态同步和 tab 切换。
- `__tests__/`：放置本目录相关的 Vitest 单元测试与回归测试。

## 静态审查建议

### 问题 1：页面职责偏重

- 问题：`index.vue` 同时负责路由读取、详情加载、tab 裁剪、在线状态映射、编辑提交和语言刷新，状态协调逻辑集中在单文件中，后续维护成本偏高。
- 改进方案：把“路由解析”“详情加载”“tab 生成”“状态映射”“保存校验”拆成独立 helper 或 composable，让页面只保留编排层。
- 实施步骤：先抽出纯函数，再把详情加载和 tab 过滤整理成可复用方法，最后收敛保存前的数据组装逻辑。
- 预期效果：页面主流程更清楚，局部修改更安全，后续加新 tab 或改状态展示时影响面更小。

### 问题 2：tab 刷新依赖临时重挂载

- 问题：语言切换后通过清空再恢复当前 `tabValue` 来刷新标签文案，这种方式可用，但耦合了 UI 生命周期。
- 改进方案：后续若框架能力允许，可以改成更明确的 tab 文案计算或 keyed 刷新策略，减少对定时器的依赖。
- 实施步骤：先确认 Naive UI 与当前 i18n 的刷新约束，再评估是否可以用计算属性或外层 `key` 方案替代。
- 预期效果：语言切换行为更直观，相关逻辑更容易定位和测试。

### 问题 3：编辑数据的回填和提交边界需要再核对

- 问题：当前页面的编辑弹窗以 store 里的设备对象为输入源，`labels` 与后端标签字段的双向回填关系需要继续核实。
- 改进方案：明确“显示值、编辑值、提交值”三者的边界，必要时在打开弹窗时同步回填 tags，在保存时只提交经过校验的字段。
- 实施步骤：对照接口字段确认标签、描述、设备编号的来源，再补一层输入初始化和提交前整理。
- 预期效果：减少覆盖写空值的风险，编辑体验更稳定，后续接口变更时更容易定位影响。

## 维护约定

- 只在本目录内放置与当前页面强相关的逻辑、说明和测试。
- 新增 `.vue`、`.ts` 或 `.test.ts` 文件时，应继续保持中文文件头或对应说明。
- 修改业务字段时，优先同步更新本 README、相邻测试和接口 mock，避免文档与实现脱节。

## 已知边界

- 本 README 只描述当前目录的静态维护约束，不代表页面已经完成端到端验证。
- 如果后续发现 `__tests__/` 只覆盖了挂载或快照场景，应补充真实业务断言，再把页面行为结论写回这里。
